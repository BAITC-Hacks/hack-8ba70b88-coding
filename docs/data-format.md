# Формат входных данных

Приложение принимает один JSON-файл в UTF-8 со схемой версии `1`. Это собственный формат MVP; совместимость с выгрузкой 1С не заявляется. CSV используется для экспорта утверждённого результата, а не для импорта исходных данных.

Рабочий пример можно скачать кнопкой **«Скачать пример JSON»** или получить командой `node scripts/generate-demo.js` из корня репозитория. Генератор создаёт `data/demo.json`; команда `npm run demo` делает то же самое. Для встроенного демонстрационного сценария файл создавать не требуется: кнопка **«Демонстрационный набор»** использует тот же генератор в браузере.

## Корневой объект

Все поля таблицы обязательны. Имена полей чувствительны к регистру.

| Поле | Тип | Смысл и ограничения |
| --- | --- | --- |
| `schemaVersion` | Число | Только `1`. |
| `name` | Строка | Название набора, от 1 до 160 символов. |
| `isDemo` | Логическое | `true` для синтетических/демонстрационных данных; `false` для подготовленного рабочего набора. Не является проверкой происхождения данных. |
| `historyStart` | Строка-дата | Первый день истории включительно. |
| `asOf` | Строка-дата | Дата расчёта и снимка текущих остатков; в историю не входит. |
| `categories` | Массив объектов | Категории товаров и параметры планирования. |
| `warehouses` | Массив объектов | Склады. |
| `suppliers` | Массив объектов | Поставщики. |
| `products` | Массив объектов | Товары. |
| `inventory` | Массив объектов | Текущие остатки и состав пар товар/склад для расчёта. |
| `sales` | Массив объектов | Строки продаж; может быть пустым. |
| `availability` | Массив объектов | Наличие по каждому календарному дню каждой пары товар/склад. |
| `inbound` | Массив объектов | Ожидаемые поступления; может быть пустым. |

`notes` в демонстрационном наборе — дополнительный массив пояснений. Валидатор не требует и не проверяет это поле. Неизвестные дополнительные поля не отклоняются и не очищаются автоматически; перед загрузкой удалите всё, что не требуется для расчёта.

## Даты, числа и идентификаторы

Даты задаются только как существующая календарная дата `YYYY-MM-DD`, например `2026-09-23`. Время суток и часовой пояс в поле не передаются; внутри расчёта используется начало дня UTC. Диапазон истории: `historyStart ≤ date < asOf`. Продолжительность истории — от 28 до 1830 календарных дней.

Числа передаются JSON-числами, например `12.5`, без кавычек, разделителей тысяч и десятичной запятой. `NaN` и бесконечность не допускаются. Дробные продажи, остатки и поступления допустимы, но количество заказа в MVP — целое число, кратное целой упаковке.

`id` и `customerId` — непустые строки до 80 символов; `name` — до 160, `unit` — до 30. Строки не могут состоять только из пробелов и содержать управляющие символы U+0000–U+001F. Значения не обрезаются и не приводятся к единому регистру: `p1`, `P1` и ` p1` различаются. Используйте короткие стабильные идентификаторы без пробелов, например `product-001`, `warehouse-01`, `customer-042`. ID должны быть уникальны внутри каждого справочника. Ссылки должны точно совпадать с существующим ID соответствующего справочника.

Значение `all` зарезервировано для фильтра «Все». Валидатор запрещает его как ID склада или категории.

## Справочники

`warehouses` и `suppliers` имеют одинаковую структуру: `{ "id": "…", "name": "…" }`.

Категория в `categories`:

| Поле | Смысл |
| --- | --- |
| `id`, `name` | Идентификатор и отображаемое название категории. |
| `reviewDays` | Период пересмотра запасов: целое число от 1 до 180 дней. |
| `safetyDays` | Количество дней для расчёта страхового запаса: целое число от 0 до 90. |
| `seasonality` | Ровно 12 месячных коэффициентов, с января по декабрь. Каждый — от 0.1 до 5; среднее должно быть 1 с допуском 0.03. |

Сезонность задаётся во входном файле, а не определяется приложением автоматически. Коэффициент `1` — средний уровень, `1.5` — на 50% выше него, `0.5` — вдвое ниже. При отсутствии сезонности используйте двенадцать единиц. Перед загрузкой нормируйте исходные коэффициенты делением каждого на их среднее. К сезонным коэффициентам не добавляйте ожидаемый годовой рост: сценарий роста выбирается отдельно в интерфейсе.

Товар в `products`:

| Поле | Смысл |
| --- | --- |
| `id`, `name` | Артикул/идентификатор и название товара. |
| `categoryId` | ID существующей категории. |
| `supplierId` | ID существующего поставщика. У товара один назначенный поставщик. |
| `leadTimeDays` | Срок нового заказа: целое число от 1 до 180 дней. |
| `packSize` | Размер упаковки: целое число от 1 до 1 000 000. Рекомендация округляется вверх до кратного упаковке. |
| `unit` | Единица измерения, например `шт.` или `м`. Все количества этого товара используют одну единицу. |

## Остатки, продажи и наличие

Строка `inventory`:

```json
{ "productId": "product-001", "warehouseId": "warehouse-01", "onHand": 25 }
```

`onHand` — текущий остаток на начало `asOf`, от 0 до 1 000 000 000. Для пары товар/склад допустима ровно одна строка. Эта таблица определяет пары для расчёта: строки продаж, наличия и поступлений без соответствующей пары в `inventory` отклоняются. Не обязательно создавать все возможные комбинации товаров и складов.

Строка `sales`:

```json
{ "date": "2026-09-22", "productId": "product-001", "warehouseId": "warehouse-01", "customerId": "customer-042", "quantity": 12 }
```

`quantity` — строго положительное количество, не больше 1 000 000 000. Несколько строк за день одному клиенту допустимы: алгоритм суммирует их для поиска разовых крупных покупок. Не добавляйте одну и ту же операцию повторно при подготовке выгрузки: идентификатора операции и автоматической дедупликации продаж нет. Отрицательные количества и возвраты не поддерживаются; их требуется согласованно обработать до загрузки.

`customerId` должен одинаково обозначать одного клиента на протяжении всей истории. Случайная смена ID для каждой продажи разрушит распознавание регулярных крупных покупок. Заменяйте исходные клиентские данные на стабильные непрямые идентификаторы до загрузки. Не используйте ФИО, телефоны, email, ИИН/БИН или их легко обратимые замены. Приложение проверяет наличие и длину строки, но **не выполняет обезличивание и не подтверждает его качество**. Это касается также названий и дополнительных полей.

Строка `availability`:

```json
{ "date": "2026-09-22", "productId": "product-001", "warehouseId": "warehouse-01", "inStock": true }
```

Для каждой пары из `inventory` требуется ровно одна строка **на каждый день** от `historyStart` включительно до дня перед `asOf` включительно. Пропуски и дубликаты отклоняются. Если в истории 28 дней и две пары, нужны ровно 56 строк.

- `inStock: true` — товар был доступен для продажи в этот день. Если продаж нет, в `sales` не требуется строка с нулём: отсутствие строк означает нулевые продажи при наличии и учитывается в оценке спроса.
- `inStock: false` — товар отсутствовал весь день. Продажи в такой день запрещены. Алгоритм оценивает упущенный спрос; отсутствие строк продаж само по себе не считается доказательством дефицита.

Бинарное наличие не описывает часы отсутствия внутри дня. Если в течение дня была продажа, модель требует `inStock: true` и не оценивает частичный внутридневной дефицит. Историческое наличие и текущий остаток — разные данные: приложение не восстанавливает товарный баланс из движений.

## Товары в пути

Строка `inbound`:

```json
{ "productId": "product-001", "warehouseId": "warehouse-01", "quantity": 50, "eta": "2026-09-27" }
```

`quantity` — строго положительное количество до 1 000 000 000; `eta` — ожидаемая календарная дата поступления. Несколько партий одной пары допустимы и суммируются по датам. Автоматической дедупликации поставок нет.

`eta` может быть раньше, равна или позже `asOf`: валидатор проверяет корректность даты, а обработка зависит от расчёта. Приход доступен в начале дня ETA. Просроченная партия не уменьшает рекомендацию, пока дата не подтверждена заново; партия после горизонта тоже не уменьшает заказ. Поздняя партия внутри горизонта учитывается с собственной даты и не закрывает более ранний дефицит. Подробности — в [методологии расчёта](methodology.md).

## Ограничения размера и проверки

| Данные | Допустимый объём |
| --- | --- |
| Каждый из `categories`, `warehouses`, `suppliers`, `products` | От 1 до 1000 строк |
| `inventory` | От 1 до 1000 пар |
| История | От 28 до 1830 дней |
| Пары × дни истории | Не больше 200 000 |
| `availability` | От 1 до 200 000 строк, точное покрытие всех пар и дней |
| `sales` | От 0 до 300 000 строк |
| `inbound` | От 0 до 10 000 строк |
| Файл в браузерном импорте | Не больше 30 × 1024 × 1024 байт (30 МиБ) |

Валидация проверяет структуру, диапазоны, корректность дат, ссылки на справочники, уникальность остатков и наличия, полное покрытие истории и отсутствие продаж при полном отсутствии товара. При первой найденной ошибке импорт останавливается с сообщением. Проверки не доказывают достоверность остатков, сроки поставок, качество обезличивания или правильность заданной сезонности. Большие допустимые наборы могут рассчитываться медленнее; отдельного серверного обработчика данных нет.

## Подготовка и загрузка своего набора

1. Скачайте пример JSON или выполните `node scripts/generate-demo.js` при установленном Node.js 20+.
2. Подготовьте обезличенные справочники и стабильные клиентские ID. Задайте дату снимка, начало истории, месячные коэффициенты и параметры планирования.
3. Заполните текущие остатки, ежедневное наличие, продажи и ожидаемые поступления. Удалите демонстрационные строки и лишние поля. Для рабочего набора укажите собственное название и `isDemo: false`.
4. В приложении нажмите **«Загрузить JSON»**, выберите файл и исправьте ошибки, если проверка их обнаружила. UTF-8 BOM в начале файла допустим.
5. Выберите склад или категорию, режим роста и запустите расчёт. Проверьте пояснения, скорректируйте количество, утвердите план и скачайте CSV. После изменения данных, параметров или количества требуется новый расчёт либо повторное утверждение по соответствующему шагу интерфейса.

Файл обрабатывается в памяти браузера. Импорт не отправляет заказы поставщикам и не вызывает внешние сервисы. Исходный JSON и утверждённый CSV — разные артефакты; CSV не предназначен для повторной загрузки исходной истории.

## Что содержит демонстрационный набор

Генератор всегда использует seed `20260923` и дату расчёта `2026-09-23`. В нём 8 вымышленных товаров, 2 склада, 3 категории и 3 поставщика; история — с `2024-01-01` по `2026-09-22`, всего 996 дней и 15 936 строк доступности.

В скрытый спрос заложены разные месячные сезонные профили, устойчивый рост 14% в год, случайный шум и недельная составляющая. Есть окна отсутствия товара, разовая покупка `350 + 275` одному клиенту за день, другая разовая покупка `800`, регулярные покупки по `80` раз в неделю и по `120` раз в месяц. Товары в пути включают ближайшие, поздние и просроченные партии. Описание этих событий доступно в `notes`. Это тестовые сигналы; оценённый моделью прирост и спрос могут отличаться от параметров генератора.
